# Notion MCP 0.4.0 — Design Spec

- **Date:** 2026-05-30
- **Status:** Draft (design) — pending user review, then implementation plan
- **Origin:** brainstorming session triggered by "make the LobeHub listing validated", "why does
  GitHub still show 0.2.0 as latest", and "does the server still load pages — did Notion change the
  URL?"

## Context

Three threads converged into one release.

1. **LobeHub shows the server as `Unvalidated`.** LobeHub's badge means their bot installed the
   server, started it, and listed its tools. Ours **crashes on startup without credentials**:
   `src/server.ts` runs `const config = loadConfig()` at module top level, and `loadConfig()` throws
   when `NOTION_TOKEN` / `NOTION_USER_ID` / `NOTION_SPACE_ID` are missing. The validator runs with no
   credentials, so the process dies before answering `initialize`/`tools/list`. The live Score tab
   also rewards **Prompts** and **Resources** (we implement neither) and **Skills** (LobeHub's word
   for tools — we have 11, but they can't be detected while the server won't boot). The LobeHub badge
   is already in `README.md`, so that item is satisfied.

2. **GitHub still lists `v0.2.0` as "Latest".** Confirmed: the only tag locally and on the remote is
   `v0.2.0` (2026-04-22). 0.3.0 was merged to `main` (PR #1) and published to npm (`latest = 0.3.0`),
   but **no `v0.3.0` tag and no GitHub Release were ever created**. GitHub's Releases panel only lists
   tagged releases. Fix = backfill the tag + release.

3. **Page loading works; the URL did not change.** Verified live against the connected server:
   `search` returned the full workspace, and **3 of 5 sampled pages exported real content** through
   `loadPageChunk` at `www.notion.so/api/v3`. Two pages returned a **silently empty** string. Root
   cause is in the converter, not the API: `from-notion.ts` *skips* child blocks of `type: 'page'`
   (sub-page links) and never fetches database/collection rows, and `export.ts` returns the empty
   result without explanation. A pre-existing coverage gap, surfaced by a database-heavy workspace.

A fourth realization while scoping the validation fix: the published `bin` is **raw TypeScript** with
a `#!/usr/bin/env bun` shebang (`"notion-mcp": "src/server.ts"`, `files: ["src"]`). That only runs
where bun is installed — so `npx @shck-dev/notion-mcp` fails for the majority of users who have node
but not bun, and it is the single biggest risk to LobeHub validation. A code scan confirms the
source is already node-clean: **zero `Bun.*` usage**, file IO already uses node `fs`, stdin is
node-style; the only non-portable line is the `../package.json` import. Shipping compiled,
node-runnable JS is therefore cheap and removes the risk entirely.

## Scope (seven workstreams)

- **0** — node-compatible build (ship `dist/`, node shebang)
- **1** — credential-free startup (lazy, memoized config)
- **2** — interactive init (shared cURL parser → config file; CLI wizard + `notion_init` tool)
- **3** — MCP prompts + resources
- **4** — empty-export fix (sub-page links + informative note)
- **5** — 0.4.0 version bump + docs + backfill the v0.3.0 release
- **6** — publish + re-validate on LobeHub

### Non-goals (explicitly deferred)

- **Full database/collection rendering.** Fetching rows via `queryCollection` and rendering them as
  markdown tables is deferred. 0.4.0 only stops the *silent* empty (renders sub-page links and an
  explanatory note). Chosen deliberately to keep the release bounded.
- **Migrating off `token_v2`.** Same stance as 0.3.0 — would break the "just a browser cookie"
  premise. Out of scope.
- **Encrypting the config file / OS keychain.** The config file is `0600` plaintext JSON (the same
  secret already lives in plaintext in the MCP client's env config). Keychain storage is deferred;
  the security trade-off is documented in WS2.

## Workstream 0 — node-compatible build

**Files:** `package.json`, `src/server.ts` (shebang), new build output `dist/server.js`.

- Build with bun, ship node-runnable JS:
  `bun build src/server.ts --target node --format esm --outfile dist/server.js`. Bundling strips TS
  types, externalizes node builtins (`fs`), and **inlines `../package.json`** so the version is baked
  at build time — the one non-portable import disappears with no runtime JSON-import workaround.
- Set the **source** shebang (`src/server.ts`) to `#!/usr/bin/env node`; `bun build` carries it into
  `dist/server.js`, and dev is unaffected because `bun run src/server.ts` ignores the shebang. The
  build script appends `chmod +x dist/server.js`.
- `dist/` is gitignored (build artifact); npm still packs it because `prepublishOnly` rebuilds it
  before the `files` set is collected.
- `package.json` changes:
  - `bin` → `{ "notion-mcp": "dist/server.js" }`
  - `files` → `["dist", "README.md", "LICENSE"]` (stop shipping `src`; the bundle is self-contained)
  - `scripts` → add `"build": "bun build src/server.ts --target node --format esm --outfile dist/server.js && chmod +x dist/server.js"` and `"prepublishOnly": "bun run build"`
  - `engines` → `{ "node": ">=18" }` (global `fetch` is available on node 18+; bun still used for dev/test)
- Dev workflow is unchanged: `bun run src/server.ts`, `bun test`.

**Test / gate:** `node dist/server.js` (no env vars) starts and answers `initialize` + `tools/list`;
`initialize.serverInfo.version` equals `package.json` version; both `npx` and `bunx` smoke-run.

## Workstream 1 — credential-free startup (lazy config)

**Files:** `src/server.ts`, `src/notion-client.ts`.

- Delete the top-level `const config = loadConfig()`.
- Add a memoized accessor: `let cfg; const getConfig = () => (cfg ??= loadConfig());`. Call it **only**
  inside the `tools/call` cases (passing the result into each tool fn). The existing `tools/call`
  try/catch already converts a thrown `loadConfig` error into an `isError` content response — so a
  missing-credentials call returns the helpful message instead of crashing.
- `initialize`, `tools/list`, `prompts/list`, `resources/list` never touch `getConfig`.

**Test:** `handleMessage` for `initialize`, `tools/list`, `prompts/list`, `resources/list` all return
results with **no env vars set** and no throw; a `tools/call` (e.g. `notion_search`) with no creds
and no config file returns `isError` content containing `NOTION_TOKEN`.

## Workstream 2 — interactive init (shared core, two front-ends)

**Files:** new `src/config-store.ts`, new `src/tools/init.ts`, new `src/cli-init.ts`,
`src/server.ts`, `src/notion-client.ts`.

**`config-store.ts`** — `configPath()` = `~/.notion-mcp/config.json` (via `os.homedir()`).
`readConfigFile(): Partial<NotionConfig> | null`. `writeConfigFile(cfg)` — `mkdir` the dir `0700`,
write JSON `0600`.

**`notion-client.ts` `loadConfig()`** — resolve each field **env → config file**, then if any field
is still missing, throw an error that now points at **both** `npx @shck-dev/notion-mcp init` and the
manual env-var route.

**`tools/init.ts`:**
- `parseCurl(curl)` — tolerant of Chrome's "Copy as cURL (bash)": line continuations (`\`), `$'…'`
  ANSI-C quoting, and `-H/--header`, `-b/--cookie`, `--data-raw/--data/-d` forms. Extracts:
  - `token` ← `token_v2=([^;'"]+)` from the cookie header (URL-decoded). **Required** (throw if absent).
  - `userId` ← `x-notion-active-user-header` header, falling back to the `notion_user_id` cookie.
  - `spaceId` ← `spaceId`/`space_id` in the JSON body, if present.
- `resolveSpaces(token, userId?)` — when `spaceId` (and/or `userId`) is missing, call the internal API
  (`getSpaces` / `loadUserContent`; exact endpoint verified during implementation) to list the user's
  workspaces as `{ id, name }[]` and resolve `userId` from the user record. From a token alone we can
  recover both `userId` and the space list.
- `notionInit({ curl, space_id? })` — `parseCurl` → resolve missing space; if several workspaces and
  none chosen, **return the list** for the agent to re-call with `space_id`; otherwise `writeConfigFile`
  and return a confirmation with the **token redacted**. Credential-free (uses the parsed token).

**`cli-init.ts` `runInit()`** — print the guide ("open Notion in Chrome → DevTools → Network → any
`/api/v3` request → Copy as cURL"), read the pasted cURL from stdin via node `readline`, parse,
resolve/prompt for the workspace, `writeConfigFile`, and print the config path plus the equivalent
`claude mcp add notion -- …` line.

**`server.ts`** — if `process.argv[2] === 'init'`, `await runInit()` then exit, before starting the
transport. Register `notion_init` in `TOOLS` and add its `tools/call` case.

**Security note:** the token is written to `~/.notion-mcp/config.json` (`0600`). The tool/CLI never
print the token (redacted in output, never logged). This is the same secret the user otherwise pastes
into their MCP client's env config; keychain storage is a deferred non-goal.

**Test:** `parseCurl` against fixtures — real Chrome cURL with a URL-encoded token, `$'…'` quoting,
a `-b` cookie form, and a body without `spaceId`; assert extracted token/userId/spaceId. `config-store`
round-trip against a temp dir, asserting `0600`.

## Workstream 3 — MCP prompts + resources

**Files:** new `src/prompts.ts`, new `src/resources.ts`, `src/server.ts`.

- `initialize` capabilities → `{ tools: {}, prompts: {}, resources: {} }`.
- **Prompts** (`prompts/list`, `prompts/get`): `notion_setup` (no args — returns the init guide as
  prompt messages, doubling as onboarding) and `notion_search_export` (arg `query` — messages that
  drive a search-then-export). Listable with no credentials.
- **Resources** (`resources/list`, `resources/read`): static `notion://guide` (markdown usage guide,
  always listable/readable, no creds) and dynamic `notion://recent` (recent pages via the internal
  API when creds resolve; its `read` without creds returns guidance text, not an error). `resources/list`
  returns both descriptors with no credentials.

**Test:** `prompts/list` and `resources/list` each return ≥1 entry with no env vars; `prompts/get
notion_setup` and `resources/read notion://guide` succeed credential-free.

## Workstream 4 — empty-export fix (sub-page links + note)

**Files:** `src/markdown/from-notion.ts`, `src/tools/export.ts`.

- `from-notion.ts` `case 'page'`: keep skipping the **root** page block, but for a **child** page block
  (`blockId !== rootId`) render `- [Title](https://www.notion.so/<id>)` so sub-page hubs are no longer
  blank. (`renderBlock` already closes over `rootId`.)
- `export.ts`: after `blocksToMarkdown`, if the result has no renderable text, return an **informative
  note** instead of an empty string — e.g. "_This page has no exportable text. It may be a database
  (collection view) or contain only embeds/sub-pages._" listing the resolvable child block types. Note:
  `collection_view` records live under `recordMap.collection_view`, not `recordMap.block`, so some
  child types may be unresolved — the note stays robust either way.

**Test:** a stubbed `blockMap` whose root's only child is `type:'page'` renders the markdown link; a
stub whose root has no renderable children returns the non-empty note, not `''`.

## Workstream 5 — 0.4.0 bump + docs + backfill v0.3.0

- **Version bump to 0.4.0:** `package.json`, `server.json` (top-level `version` and
  `packages[].version`), `CLAUDE.md` ("currently 0.3.0").
- **`README.md`:** add the init flow (CLI wizard + `notion_init` tool), prompts/resources, the fact
  that `npx` now works without bun, and the databases/sub-page-hub note under limitations.
- **`CLAUDE.md`:** new files in the architecture tree, `notion_init` in Tools, a Prompts/Resources
  section, the sub-page-link mapping, and an updated Known-gaps entry (databases).
- **Backfill v0.3.0 release:** `git tag v0.3.0 a7250f9` (the 0.3.0 merge commit) and
  `gh release create v0.3.0` with notes drawn from the 0.3.0 features (to-do/strikethrough, append
  tool, actionable auth errors). The release's created-date will be "now" while the tag points at the
  historical commit — acceptable; npm already carries 0.3.0.

## Workstream 6 — publish + re-validate on LobeHub

- `prepublishOnly` builds `dist/`. **Maintainer runs** `npm publish --access public --otp=<code>`.
- `gh release create v0.4.0` with the 0.4.0 notes.
- After npm propagates, drive Playwright to the LobeHub page → click **Refresh Metadata** → verify the
  badge flips from **Unvalidated** to **Validated** and the Score items **Skills / Prompts / Resources**
  go green. A re-scan may lag the click; if it doesn't flip immediately, re-check after a scan cycle.

## Testing & sequencing

- **Gate:** `bun test` green + `bun run typecheck` clean + `node dist/server.js` boots credential-free.
- Existing `tests/integration/` may require live credentials (per 0.3.0). All **new** tests are pure
  unit tests — mock `fetch`, use temp dirs/`HOME`, call converters/parsers directly — so they run offline.
- Implement as ordered, isolated commits on a `feat/0.4.0` branch: WS0 → WS1 → WS2 → WS3 → WS4 → WS5,
  then WS6 (publish/validate) last. WS0+WS1 alone are sufficient to flip validation; the rest raises the
  score and ships the init feature.

## Open risks

- **bun-build version inlining** — verify post-build that `initialize` reports the right version.
- **`parseCurl` across browsers** — target Chrome's bash form (fixtures); tolerate Firefox best-effort.
- **`resolveSpaces` response shape** — confirm `getSpaces`/`loadUserContent` fields against the live API.
- **Plaintext token on disk** — mitigated by `0600`; documented; keychain deferred.
- **LobeHub re-validation latency** — the badge may not flip on the first Refresh Metadata.
- **Node-only validator assumption** — fully mitigated by WS0 (node build), no longer a bet.
